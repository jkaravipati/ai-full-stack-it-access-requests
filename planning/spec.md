## Open questions

Research reviewed the four source files, all 20 supplied exports, the repository's classroom instructions and starter checks, and the primary format documentation linked below on 2026-11-13. `python3 tools/check_prerequisites.py` reported `READY`. Findings below distinguish what the text resolves from questions it leaves open; they do not add requirements or select an implementation. “Open” can mean a documented design choice rather than something requiring facilitator clarification.

| ID | Question | What the research found | What stays open |
|---|---|---|---|
| Q-01 | Which interface, language and provider are required? | [CHALLENGE.md, The task](../CHALLENGE.md) explicitly permits a CLI, service or web application; [requirements, Record and review behavior](../docs/requirements.md) requires configurable model/provider settings and a documented supported configuration. [Prerequisites](../docs/00-prerequisites.md) requires Python 3.10+ for the course setup, but does not say the application must be written in Python. | Application language, interface, storage, provider, model ID, endpoint and supported deployment remain design choices; no provider-specific response contract can be established until one is selected. |
| Q-02 | Must deliverables or tests use live model responses? | [CHALLENGE.md, Submission](../CHALLENGE.md) explicitly allows mocked or provider-generated committed deliverables and requires an implemented provider integration; its accuracy row calls live observations optional. [Planning instructions, step 2](../docs/02-plan-with-test-plan.md) say no test calls the real model or needs API_KEY. The prerequisite check passed with API_KEY unset. | No mandatory live-run count or live accuracy threshold is specified; mock-based checks alone cannot establish live extraction accuracy. |
| Q-03 | What counts as a complete or valid extraction? | [Schema](../snapshot.schema.json) requires all 14 keys but permits null scalars. [Policy, Review queue](../materials/office-policy.md) separately defines business-required facts for new/change requests, and an exception for withdrawals. [JSON Schema object documentation](https://json-schema.org/understanding-json-schema/reference/object#required) distinguishes property presence from a null value. Thus schema validity alone does not establish business completeness. | How semantic validation is reported internally remains unspecified; it must be distinguished from structural validation and policy routing. |
| Q-04 | Which JSON Schema dialect and validator should be used? | [snapshot.schema.json](../snapshot.schema.json) contains no `$schema` declaration. [JSON Schema dialect documentation](https://json-schema.org/understanding-json-schema/reference/schema#schema) says implementations may accept an external dialect choice or assume one when the declaration is absent. | The validator, dialect and any provider-specific translation of the supplied schema are unspecified. |
| Q-05 | Are empty strings valid facts, and how are impossible dates handled? | The [schema](../snapshot.schema.json) has no `minLength`, date `format` or date `pattern`. [JSON Schema string documentation](https://json-schema.org/understanding-json-schema/reference/string) confirms that a string type permits empty strings and length constraints are separate. The [policy, Extracted facts](../materials/office-policy.md) requires explicit facts and YYYY-MM-DD dates. [RFC 3339 §5.6](https://www.rfc-editor.org/rfc/rfc3339#section-5.6) describes a full-date with calendar-constrained month/day values, but the brief does not adopt that RFC explicitly. | Treatment of whitespace-only fields, impossible dates and semantically invalid but schema-valid strings is not stated; the RFC does not choose the application's error-versus-clarification behavior. |
| Q-06 | Can dates be inferred from metadata, relative wording or nearby dates? | [Policy, Input export format and Extracted facts](../materials/office-policy.md) explicitly makes message the factual source and leaves relative dates unresolved. [IT-011](../materials/requests/IT-011.json) gives an absolute request date but only “next Monday - Friday” for access dates; [IT-010](../materials/requests/IT-010.json) supplies no fixed end date. Those facts resolve these cases without using exported_at as a date anchor. | Handling ambiguous numeric dates, omitted years, partial dates and equal start/end dates is not further defined. |
| Q-07 | What qualifies as an explicitly labelled correction? | [Policy, Extracted facts](../materials/office-policy.md) distinguishes corrections from unresolved contradictions. [IT-008](../materials/requests/IT-008.json) explicitly corrects production to staging and [IT-015](../materials/requests/IT-015.json) explicitly substitutes dates; [IT-004](../materials/requests/IT-004.json) and [IT-020](../materials/requests/IT-020.json) contain uncorrected environment and manager contradictions. | Whether wording such as “actually,” “ignore my previous date,” multiple corrections or a correction introducing a relative value qualifies is not defined beyond the general rule. |
| Q-08 | How much normalization or paraphrasing is allowed in extracted facts? | [Policy, Extracted facts](../materials/office-policy.md) requires explicit facts, but only supporting quotes must be exact substrings. [IT-013](../materials/requests/IT-013.json) uses “reading” where the enum value is read; [IT-007](../materials/requests/IT-007.json) requests a transition from read to write without using the word change.
