# Build plan

## Choices

- **Runtime:** Python 3.10+ with a package named `access_intake`, standard-library `unittest`, `sqlite3` and HTTP transport, plus a pinned JSON Schema validation dependency and transitive dependency lockfile; this fits the supplied Python setup and keeps the application small.
- **Interface:** a CLI plus a local HTTP service and browser dashboard, as explicitly requested by the user after the original CLI plan. All three share the same SQLite store and extraction pipeline. The service accepts intake/retry/resume asynchronously, exposes current records/history, and serves responsive buildless HTML/CSS/JS; no frontend dependency installation or public hosting is required.
- **Test command:** `env -u API_KEY python3 -m unittest discover -s tests -v`; every new test blocks outbound networking, uses temporary state and a mock provider or injected HTTP transport, and requires no real credential.
- **Model call:** an OpenAI adapter using HTTPS POST to `https://api.openai.com/v1/responses` with model `gpt-5.6-terra`, `reasoning.effort: none`, `max_output_tokens: 4096`, `stream: false`, `store: false`, no tools, and strict JSON Schema output through `text.format`; omit temperature/top_p and other optional sampling settings. Read `API_KEY` only in live mode. Record the full effective request configuration and the response's returned model ID. The [model documentation](https://developers.openai.com/api/docs/models/gpt-5.6-terra), [Structured Outputs guide](https://developers.openai.com/api/docs/guides/structured-outputs) and [Responses reference](https://developers.openai.com/api/reference/resources/responses/methods/create) support this planned adapter configuration; documentation was checked on 2026-11-13. Provider/model/endpoint/token limit remain configurable. Tests inject the HTTP transport and credential accessor; no live request or actual account access is required or claimed.
- **Storage:** one shared local SQLite database on one host, with short transactions, no database transaction held during model calls, and persistent input bytes, attempts, settings, policy versions and results; regional operators use that host rather than sharing a database over a network filesystem. Begin with SQLite's default rollback journal and bounded lock waits; no multi-host guarantee is claimed. The [SQLite documentation](https://www.sqlite.org/wal.html) describes WAL as an optional alternative rather than a prerequisite for SQLite transactions.
- **Output publication:** SQLite is authoritative; queue inspection reads one database snapshot. At an export snapshot with no queued/running current targets, write the extraction/queue pair and manifest into a new generation directory, then publish through one atomically replaced `current` pointer; fixed deliverable paths resolve through that generation. Allocate monotonic export sequence numbers and serialize the short pointer-publication operation under the shared store's lock, refusing publication of a sequence older than the published one. Refuse final export while current targets are unfinished and report their document IDs; operators still inspect completed results through the CLI during intake. Export readers resolve `current` once and pin that generation for both files. Plain sequential opens of the fixed paths across a pointer switch are not a consistent-reader protocol. Prior attempt results remain separately inspectable in history.
- **Configuration provenance:** fingerprint original source bytes plus provider, endpoint, configured model ID, effective request parameters, extraction and override-assessment prompt bytes, supplied/wrapper/assessment schema bytes, extraction implementation version and policy bytes/version; exclude credentials, worker count, lease timing, logging settings and request timeouts. A relevant change creates a fresh extraction attempt, including policy-only changes; retain the old result with its producing configuration. This conservative refresh avoids silently reusing records under a changed policy. Provider changes behind an unchanged model alias cannot be detected in advance; record returned IDs and provide explicit retry/refresh rather than claiming immutable model behavior.
- **Recovery:** store work claims with a 180-second lease, renewed every 30 seconds, and a monotonically increasing fencing token on each claim/reclaim. A worker may publish only while its token is valid and its target generation remains current; terminal writes and queue changes share one transaction. Resume reclaims expired work, preserves unexpired claims and completed results, and never retries terminal errors automatically. A process crash can repeat a provider call; stale responses cannot overwrite the current result.
- **Scheduling:** four workers and a configurable 60-second deadline per model call; a message can make one extraction call and, only when an override candidate exists, one additional context-assessment call, each covered by the worker heartbeat. HTTP 429/5xx, connection errors and timeouts become visible terminal errors with explicit retry commands, without automatic sleeping/backoff or retry loops. Other queued messages continue. An injected clock and synchronization barriers test deadlines and leases without real waits. These are implementation defaults, not workload acceptance thresholds.
- **Fixture boundaries:** author source-grounded expected facts before any implementation. Mock responses are separate files from expected fixtures, even when they intentionally contain the same facts. Passing mock tests demonstrates validation, routing and recovery behavior, not live language-model accuracy.

## Steps, in build order

For each step, write its owned tests first, run them and observe a meaningful failure because the behavior is absent; then implement only that step's behavior and run those tests plus appropriate earlier regression tests. A test is owned by exactly one step, although later steps may run it again. All commands use mock responses or injected transports and need no API_KEY. These are future build instructions, not work performed during planning.

1. **Build the mock provider first.** Owns **T-01**; meets R-18 and establishes the mock side of R-07/R-34. Provide fixture-backed responses for extraction and override_assessment operations, scripted errors, blocked responses controlled by barriers, per-operation call counts and injectable time. Done when canned replies can be retrieved without a key or network and tests fail on attempted real networking. The starter canned reply is illustrative, not an extraction oracle.
2. **Load exports and validate the supplied extraction schema.** Owns **T-02, T-03**; meets R-30/R-41/R-42/R-44/R-45/R-46/R-71–R-76. 3. **Build source-grounded fixture expectations, extraction instructions and ordered routing.** Owns **T-04–T-16, T-37–T-39**; meets R-35/R-36/R-47–R-65 and the routing side of R-33. - `python3 -m access_intake queue --state .state/intake.sqlite3`

- `python3 -m access_intake resume --state .state/intake.sqlite3`

Provider choice and effective configuration persist with attempts so resume/retry cannot silently switch providers or settings. Live mode uses the same intake command with `--provider openai` and optional `--config <path>` to override the documented defaults; setup and verification remain possible without API_KEY. Normal intake reuses unchanged errors, retry forces a new attempt, and resume excludes terminal errors as specified in D-3. CLI names are planned choices, not pre-existing commands.

The user-requested service/web extension uses `serve --provider mock --host 127.0.0.1 --port 8000 --input-root materials/requests --output deliverables`. GET routes provide /api/health, /api/config, /api/queue, /api/documents/<id> and /api/documents/<id>/history. POST /api/intake accepts {} for the configured input directory or an exports array of filename/data_base64 objects; POST /api/resume and /api/documents/<id>/retry enqueue work; POST /api/export publishes a quiescent snapshot. Uploaded names are unique flat JSON basenames, and raw bytes are retained. No API accepts an arbitrary filesystem path. The UI exposes upload/start, filters, details/source/quotes/issues, history, retry/resume and export downloads. The service binds loopback; cross-origin mutations and unrecognized Host values are rejected. Requests are limited to 8 MiB, 128 KiB per decoded file and 2,000 files; the browser applies a 5 MiB decoded-batch limit. These are implementation limits, not new source requirements.
